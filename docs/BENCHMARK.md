# 容量压测：10 万 SKU / 100 万价格点

- 时间：2026-10-21 20:52（UTC+8）；机器：8 核 CPU 的单机（box），单进程；脚本 `scripts/bench_scale.py`，原始数据 `docs/bench/*.json`。
- 数据：10 万商品（200 个平台、10 个类目、2 万个同款组），每个商品 10 个价格点，共 100 万点。
- PostgreSQL 17 为本机默认配置，未调优。

## 写入
| 指标 | SQLite | PostgreSQL |
|---|---|---|
| 写入 10 万商品 | 1.6 秒 | 2.1 秒 |
| 写入 100 万价格点 | 3.9 秒（约 25.8 万点/秒） | 13.0 秒（约 7.7 万点/秒） |
| 首次启动补算 100 万点置信度 | 20.4 秒 | 33.6 秒 |
| 占用空间 | 224 MB | 461 MB |

> 压测中发现：旧版置信度补算逐行查询、逐行提交，100 万点时启动 15 分钟以上仍未完成。已改为单次扫描 + 内存维护历史 + 每 5000 条批量写回，降到 20–34 秒。

## 查询延迟（毫秒，P50 / P95）
| 查询 | SQLite | PostgreSQL |
|---|---|---|
| 单品最新价 | 0.42 / 1.23 | 0.16 / 0.24 |
| 单品历史（全部点） | 0.30 / 0.96 | 0.21 / 0.29 |
| 同款组比价 | 0.15 / 0.21 | 0.20 / 0.26 |
| 按平台分页 50 条 | 0.33 / 0.63 | 1.00 / 1.29 |
| 标题模糊搜索 LIKE | 4.9 / 5.5 | 11.4 / 17.6 |
| 分页接口 /api/catalog/page（含总数和最新价） | 7.2 / 9.3 | 70 / 92 |
| 全量最新价聚合（100 万点） | 111 | 338 |
| 按类目统计均价（100 万点连接） | 433 | 127 |

## 向量检索（10 万 × 384 维，单条查询 top-10）
| 引擎 | 建索引 | P50 | P95 | top-1 召回 |
|---|---|---|---|---|
| FAISS Flat（精确） | 0.15 秒 | 36.8 ms | 41.0 ms | 100% |
| FAISS HNSW（近似） | 32.5 秒 | 0.80 ms | 1.03 ms | 99.5% |
| numpy 矩阵乘（精确，对照） | — | 1.07 ms | 4.97 ms | 100% |

结论与调整：单条查询时，FAISS Flat 反而比 numpy 慢（多线程 BLAS 的矩阵乘更快）。因此自动策略改为：不足 5 万条用 numpy 精确检索，5 万条及以上用 FAISS HNSW（快约 45 倍于 Flat，召回 99.5%）。

## 结论
- 单机 SQLite 能轻松承载 10 万 SKU / 100 万点：单品查询都在 1 毫秒级，分页接口小于 10 毫秒。
- PostgreSQL 的点查更稳（P95 更低），聚合连接更快；但未调优时批量写入和带 COUNT 的分页较慢。团队版建议：调大 `shared_buffers`，写入用 COPY，总数改为缓存或估算。
- 旧接口 `/api/products` 一次返回全部商品，大规模时应改用 `/api/v1/catalog/page`。
- 结果可外推到 100 万 SKU / 1 亿点（见 ARCHITECTURE 第 11 节）：单机 SQLite 约 22 GB 仍可用，但全量聚合会到 10 秒级，这一档应换 PostgreSQL 分区或 TimescaleDB。
